# F11 — Index update fallback without write access to Index

## Status

- First independent review F1–F10: passed in second independent audit.

- The WebRPG-org/index repository and its workflows remain untouched.

## Design and trigger contract

The deploy.yml workflow retains push(main), workflow_dispatch (optional pinned frontend and source SHA), and repository_dispatch(index-updated). It additionally schedules a read-only check every six hours using the UTC cron expression 23 */6 * * *. GitHub schedules activate only once the workflow exists on the default branch, and can be delayed by GitHub scheduler load.

On a scheduled run:

1. Checkout the current frontend commit and resolve WebRPG-org/index refs/heads/main using git ls-remote, validating an exact 40-hex commit SHA.
2. Fetch the deployed https://webrpg.org/build-manifest.json over HTTPS with a cache-busting query. The manifest is generated by the SSG verifier and deployed with the site. An unavailable, invalid or outdated manifest fails OPEN to running full validation rather than silently losing updates.
3. If frontend SHA and source SHA both match the deployed manifest, exit successfully without npm ci, Astro build or publishing.
4. Otherwise pin INDEX_REF to the verified SHA, install dependencies, run the full existing CI (source schema, ESLint, Astro TypeScript, unit tests, static build and SEO route audit).
5. Compare the valid generated manifest to the deployed manifest: only a changed normalized catalogHash, changed routesHash or changed frontend commit authorizes a Pages candidate. A changed upstream SHA due only to checkedAt or audit logs must not publish.
6. Only a meaningful candidate runs Chrome/Playwright browser regression, artifact preparation, Pages upload and deploy job. Build failures always stop deployment.

On push/main, manual or repository_dispatch, preserve existing behavior: build, validate, run browser checks, publish. No Index write token or additional cross-repository secret is required.

## Limits and costs

- Six-hour detection cadence is a trade-off: Index changes may take up to the next scheduled window (plus scheduler/build delays). It is not instantaneous push-triggered publication.
- A changed upstream SHA that proves to be audit-only can still incur one full build per scheduled run until meaningful content is published; the hash comparison avoids unnecessary DEPLOYMENTS, not all build minutes.
- Access to the deployed manifest URL is required for an efficient skip. Any fetch failure leads to a safe build and possible deployment instead of a skipped update.
- Only a real GitHub-hosted Linux scheduled run can prove Actions permissions, Pages artifact handoff, Chrome path and end-to-end live behavior; local fixtures only validate the release decision logic.
- Do not claim F11 production-complete before the workflow exists on default branch and a scheduled event has been observed.
